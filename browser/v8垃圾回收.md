# V8 引擎垃圾回收（GC）机制总结

## 1. 核心思想

依据**弱分代假设**——大多数对象寿命极短，只有少数能长期存活。V8据此把堆划分为**新生代**和**老生代**，对两代采用不同回收策略。

```
堆
├── 新生代   → 新对象，回收频繁
└── 老生代   → 长寿对象，回收稀疏
    └── 大对象空间（Large Object Space）
```

## 2. 如何判断垃圾

**两代统一——只依据可达性（Reachability）**：

- 以**根集合**（全局对象、调用栈变量、参数、寄存器、活动闭包、内建对象）为起点遍历。
- 从根可达 = **存活**；从根**不可达 = 垃圾**，可回收。
- 垃圾 ≠ 被赋 null，而是"从根无法再访问到"。引用被切断既成垃圾。

> 新生代根集合 = 栈+全局+寄存器（轻量）；
> 老生代根集合 = 栈+全局+**记忆集引用**（跨代引用，避免重扫新生代）。

## 3. 新老生代回收与新生代晋升

### 新生代回收：Scavenge（Minor GC）

- **半空间机制**：新生代分为两块等大的 **From**（分配新对象）和 **To**（GC时接收存活对象）。
- **流程**：新对象分配进 From → 空间不足触发 GC → 从根遍历标记存活对象 → 把存活对象复制到空的 To，死亡对象丢弃 → **交换 From/To 指针**，本轮结束。
- **复制算法（Cheney）**：只复制存活对象，速度快；每次 GC 开始 To 必为空。

### 晋升（新生代 → 老生代）

| 场景                    | 触发条件                                           |
| ----------------------- | -------------------------------------------------- |
| **存活够久**（主动）    | 对象经历足够轮次的 Minor GC 仍存活（age ≥ 阈值）   |
| **To 空间溢出**（兜底） | 存活对象总量超过 To 可容纳空间，放不下则晋升       |
| **对象过大**            | 超过阈值（约 128KB），直接进大对象空间（属老生代） |
| **存活率过高**          | 为保证复制成本，促进更早晋升                       |

> **"To 满了咋办"**：不会暂停 GC，放不下的存活对象**直接晋升到老生代**。

## 4. 老生代回收

### 为何不用复制法

老生代对象存活率高、寿命长，复制要搬动大量长命对象而清不掉几个，成本极高。因此**标记出"死的"再清除**。

### 算法

1. **标记**（Mark）：白/灰/黑三色标记，从根遍历把可达对象染黑（存活）。
2. **清除**（Sweep/Compact）：
   - Mark-Sweep：删除未标记（白色=垃圾）对象，但产生内存碎片。
   - Mark-Compact：把存活对象向一端移动整理，消除碎片，代价更慢。
   - 按需切换：碎片化严重用 Compact，否则用较快的 Sweep。

### 减少停顿（Stop-The-World）

- **增量标记**：标记拆成小块穿插于 JS 执行中。
- **并发标记**：后台线程并行标记。
- **惰性清扫**：清理延迟执行。
- **并行压缩**：整理阶段多线程分工。

## 5. From → To 时的溢出

直觉上 `From = To` 应该永不溢出，但实际存在三个缺口：

1. **To 需预留缓冲**：GC 结束后立即要有空间给新分配，避免触发后又立刻再 GC（乒乓效应），故 To **不能塞满**。
2. **元数据与对齐开销**：半空间头部结构、地址对齐、指针修复占空间，To 实际可用略小于表面容量。
3. **存活率无下限保证**：From 可能被全部存活对象塞满，复制需求 ≈ 整个 From > To 实际可用 → 溢出。

**因此**：设计者**必须**保留"晋升到老生代"作为兜底，而不能赌"存活必小于半空间"。
